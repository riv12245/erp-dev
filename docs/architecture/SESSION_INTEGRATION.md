# Web and mobile API session

## Server contract and rollout

The API owns `auth_sessions` in MongoDB. A refresh credential is a random session UUID plus 256 random bits; only its SHA-256 hash and hashes of previously consumed credentials persist. Atomic compare-and-swap rotation moves the current hash to the used set. Reuse of a known consumed token revokes that session; random guesses do not revoke someone else's session. A simultaneous refresh pair can return one 200 and one 401, but the detected reuse revokes the family, including the winner's access token. Clients coordinate refresh to avoid this legitimate-race logout.

Access JWTs carry `sid`. Every authenticated request checks the current Mongo session, absolute expiry, user status/version, tenant, membership and roles. Revocation has no access-token grace window after the next authorization check; already-authorized in-flight work is not rolled back. `logout-all` increments the global user's `authVersion` atomically and invalidates older sessions across all of that user's tenants, including concurrent issuance that read an older version. A missing version on an existing user means zero.

Refresh uses `JWT_REFRESH_EXPIRES_IN` (default 7 days, maximum 30 days), does not extend absolute expiry, and caps one family at 512 rotations to bound its used-hash history. Reaching that cap requires login again. Access TTL defaults to 15 minutes and is capped at one day. Refresh/session writes fail closed on database or audit failures: the caller may have to sign in again after an uncertain rotation. An audit insert is not transactionally coupled to a session mutation; it cannot undo revocation and no success is returned if audit recording fails.

Web uses same-site deployment (local `localhost` ports, or HTTPS frontend/API on the same site). `x-session-client: web` plus an exact allowed `Origin` is mandatory for login, refresh and logout. Cookies are host-only, HttpOnly, SameSite Strict, path `/api/v1/auth`, and Secure in production. The API never returns web refresh credentials in JSON. Native/default transport accepts body credentials and rejects browser Origin. Cross-site web deployments are unsupported by this policy and require an explicit CSRF/transport design; do not fix them by allowing arbitrary origins. CORS alone is not the CSRF check.

Existing sid-less JWTs require a fresh login after rollout. Deploy API support before clients, and retain the legacy login `accessToken` and `user` fields. Refresh/logout are additive endpoints. The older `@erp/auth` token-pair/session helper exports are not the API session implementation and do not provide these persistence/reuse guarantees.

Before rollout, inspect indexes in a backed-up staging copy. The additive collection needs unique `{sessionId:1}`, `{userId:1,tenantId:1}`, and TTL `{purgeAt:1}` with `expireAfterSeconds:0`. The API calls model initialization on session creation; when production auto-indexing is disabled, create these named-by-key indexes explicitly before traffic. No destructive `syncIndexes`, collection rename, bulk user update or deletion is required. Verify duplicate keys before building a unique index; stop and investigate conflicts. Roll back application code only after considering that older API versions do not enforce session revocation.

Session rows expire through `purgeAt` seven days after absolute refresh expiry; expiry is checked in application code regardless of TTL monitor timing. Audit logs and events have no automatic deletion policy. Retention/export periods need a business decision; never delete inbox deduplication records while replay of the corresponding events remains possible. Session/audit events retain IDs, action and bounded correlation metadata, never access/refresh tokens or passwords. API 401/403 logs retain code and correlationId only.

- Login uses `@erp/api-client`, including timeout, error normalization and correlation ID.
- Web uses `VITE_API_URL` (default development API `http://localhost:3000`).
- Mobile exposes `configureApi(absoluteUrl)` in `apps/mobile/src/services/api-config.ts`; native startup reads `NativeModules.ErpConfig.API_BASE_URL`, compiled from `ERP_API_URL`. Android emulator default is `http://10.0.2.2:3000`. Physical devices need the development machine's reachable LAN URL. Release builds require HTTPS. See `ANDROID_DEVELOPMENT.md`.
- The authenticated store owns the token and tenant. Tenant UI state is a projection and never an authorization source for HTTP headers.
- Login/logout clears tenant and permission projections. Late responses from an earlier login cannot overwrite a new session or reverse logout.
- Access tokens remain in memory. Startup restores through `/api/v1/auth/refresh`; web sends credentials and the `x-session-client: web` header using the server's HttpOnly refresh cookie. Native uses `x-session-client: native` and the refresh token in JSON. Login and refresh return the authenticated tenant and session identity.
- Native refresh tokens are encrypted with AES-GCM by `ErpSecureSessionModule` using a non-exportable Android Keystore key. Only ciphertext and IV enter private preferences; backup is disabled. No Expo or plaintext token storage is used. Missing secure storage fails closed.
- Logout clears in-memory auth immediately and persists a non-secret signed-out marker before revocation. Native removes its saved token; web retains the marker across reloads because JavaScript cannot remove an HttpOnly cookie offline. A failed network revocation is reported as local logout only. A new explicit successful login clears the marker. Offline logout cannot guarantee remote revocation.
- Both dashboards expose current-session and all-device logout. All-device logout obtains a fresh access credential without restoring UI or durable storage before calling `/api/v1/auth/logout-all`, so an expired in-memory access token does not prevent revocation. Android also restores/refreshes when the app becomes active after backgrounding.
- Shared session mutations serialize and use an epoch fence. Late login/refresh results are discarded and their new refresh credential is revoked when possible. Concurrent refresh uses one flight. API reads retry once after 401; writes retry only with both an idempotency key and an explicit endpoint idempotency guarantee. Supplying a key alone does not allow replay.

Validation: `npm test -w @erp/web` includes mocked web/mobile login contracts, restore, refresh concurrency, logout races, offline logout, storage failures and retry safety. `apps/web/test/session-http.test.ts` additionally runs the actual shared client/controller against Express and disposable Mongo over loopback HTTP: native login, concurrent expired-access reads, new-controller restore and revocation; web cookie issuance, rotation, restore and logout without JSON refresh credentials; logout-all revoking another real session. Its Node cookie-jar adapter forwards real server cookies; it does not prove browser cookie policy or Android Keystore behavior. Native secure storage still requires device validation. Single-flight coordination is per client runtime, not across independent browser tabs.
